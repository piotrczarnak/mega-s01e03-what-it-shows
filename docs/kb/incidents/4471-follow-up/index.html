Problem A: shared parser reads day-first dates month first

The tenant directory establishes the date convention. For day-first tenants, the shared parser treats a day/month input as month/day. The export assigns app and email reports, and reports from the older booking-v2 form, to this parser mechanism. A booking-v3 tenant using app or email still belongs here: the tenant’s form version does not turn every channel into a form report.

Evidence: R-41200 (Harbour Dental, app, en-GB) describes 7 April becoming 4 July. R-41248 (Long Table, form, it-IT, booking-v2) describes agreed 8 May appearing as 5 August. These swapped components are consistent with the parser path in causes.ts. The unusual reports in the review table remain a qualification on the grouped count.

Proposed correction: parse using an explicit, validated input format aligned with the tenant, and retain an unambiguous internal representation. Do not use browser locale as a substitute for the tenant’s contract. Reject impossible dates instead of silently coercing them.

Acceptance checks: a day-first 07/04/2026 stays 7 April across app, email and booking-v2; 13/04/2026 remains valid and impossible dates fail clearly. A month-first tenant’s supported input still works. Verify the stored booking and invite, not just the field display. These are proposed product tests; the export does not contain the production parser.

Problem B: booking-v3 hint tells people to type the opposite format

For a day-first tenant using booking-v3, the form prints MM/DD/YYYY but interprets its input using the tenant’s day-first convention. Following the hint therefore swaps the intended date. This is a UI contract bug, not the same correction as fixing the shared month-first parser.

Evidence: R-41230 (Copper Studio, form, es-ES, booking-v3) describes intended 6 January appearing as 1 June, despite intake tagging it parser. R-41241 (Alder Physio, form, de-DE, booking-v3) describes intended 6 August appearing as 8 June. The directory also places Pale Harbour on this version; its form reports belong to this mechanism.

Proposed correction: derive the field hint, example, validation and parsing from one explicit date-format contract for that tenant. Do not change parsing to follow a misleading hard-coded hint.

Acceptance checks: for a day-first tenant the v3 hint says DD/MM/YYYY, entering 06/01/2026 books 6 January, and the stored booking and invite agree. Check all v3 tenant locales, plus v2 and app/email regressions. A parser-only fix must not be accepted as proof that the hint is fixed.
